# Contributing to CrisisOS

Keep changes understandable, deterministic, and explicitly fictional. The application must work without a backend or external runtime services.

## Development

```sh
npm ci
npm run dev
```

Use Node 22.13+ (22.x), 24.x, or 26+ and a recent browser. Before submitting:

```sh
npm run format
npm run lint
npm run format:check
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

Screenshots under `docs/` are generated by the screenshot tests. Include updated screenshots when the visible UI changes; avoid unrelated screenshot churn. Keep rule tests focused on behavior, timing, thresholds, and cross-system consequences.

## Add a scenario

1. Add an entry to the typed `scenarios` array in `src/simulation/scenarios.ts`. IDs must be unique stable URL-safe strings. Start with a copy of a preset and tune one condition at a time:

   ```ts
   {
     id: 'northbank-night',
     name: 'Northbank after dark',
     subtitle: 'Northern grid fault',
     description: 'Northbank trips during evening peak demand.',
     initialFailures: ['north'],
     demand: 1.1,
     cascadeThreshold: 45,
     backupDrain: 6,
     trafficBase: 24,
     seed: 9012,
   }
   ```

2. Use station IDs from `city.ts`: `west`, `north`, `central`, `east`. Provide at least one initial failure. Demand must be positive; the stress threshold should be in `(0, 100]`; battery drain and base congestion should be in `[0, 100]`. The seed is an unsigned 32-bit integer.
3. Add `public/scenarios/northbank-night.json` with `{ "version": 1, "scenario": "northbank-night", "seed": 9012, "actions": [] }`.
4. Add a focused rule test asserting the intended difference. Existing parameterized determinism and bounds tests automatically cover all registered presets.
5. Add the preset to the README table and inspect it in the UI. The selector, URL validator, import, comparison, and replay automatically use the registry.

JSON files select installed scenarios and schedule interventions; they cannot redefine the physics or topology. A new preset is a source contribution followed by a rebuild.

## Add an event type

1. Extend `EventKind` in `src/simulation/types.ts`, for example with `'reserve-restored'`.
2. Add its display metadata to `eventTypes` in `src/simulation/events.ts`:

   ```ts
   'reserve-restored': { label: 'Reserve restored', tone: 'success' },
   ```

3. Emit it in `simulate()` in `src/simulation/engine.ts` at the rule transition. For example, after hospital reserves update:

   ```ts
   if (prev.backup < 100 && backup === 100) {
     emit(
       'reserve-restored',
       `${h.name}: reserves restored`,
       'Battery reserve has returned to 100%.',
       h.id,
     )
   }
   ```

4. Test that the event occurs at the correct step and only once per threshold crossing. Also test replay determinism. Event IDs follow `tick-kind-asset`; choose a distinct key if emitting multiple same-kind events for one asset in a step.
5. The event stream picks up the new type and severity automatically. Update the Guide and README if the underlying rules change.

Events are a record of simulation transitions. Adding a new event type does not by itself alter the simulation. If the event should affect the city, implement and test that state change in the engine before emitting the event.

## Rule changes and reproducibility

- Use the seeded `noise(seed, tick, assetId)` helper for variation. Do not use `Math.random`, current time, timers, external data, or unordered side effects inside the engine.
- Update all station stress from one pre-cascade station snapshot so iteration order cannot trigger same-step cascades.
- Never mutate scenario inputs, action inputs, or previous snapshots.
- Keep interventions chronological, unique per kind/target, within the resource budget, and effective within the horizon. `validateFile()` enforces this at the sharing boundary; UI dispatch uses the same eligibility and costs.
- Preserve scenario and asset IDs for saved links. Rule or topology changes can change old replay outcomes; if compatibility is broken, introduce a new format/model version and reject unsupported versions clearly. Version 1 links are deterministic within this implementation, not a promise of cross-version numerical compatibility.
- If changing costs, timing, or kinds, update `types.ts`, `engine.ts`, `sharing.ts`, the response dialog, README, and tests together.
- Avoid real emergency predictions, real personal data, and claims of validated real-world accuracy.
